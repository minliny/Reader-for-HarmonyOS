# Atomic snapshot: minimal unresolved platform question

The production SourceSwitchIntentStore now delegates actual AtomicFile start/end/finish, published base-file fsync, parent-directory fsync and handle close to ReaderAtomicSnapshotFile. Local complete-DTO/lost-ACK/cold/warm tests execute this exact helper. Installed SDK declares the API, but neither source review nor a Node model proves that the target can open/fsync the parent directory, handle a >8192-character complete TOC or return a durable acknowledgement. A normal Preferences string cannot carry this data.

The required first target question is narrowly scoped: does that exact helper complete on the current OS for one synthetic 6000-entry original-shaped DTO, does exact readback match, and does exact empty replacement complete? Crash/restart durability, real Core transactions, Want authorization, reader layout/performance and user acceptance are different exits.

ReaderAtomicSnapshotProbe is an explicit **cold debug Want** `readerAtomicSnapshotProbe=true` only. Normal/release starts and warm file Wants do no diagnostic IO. It runs after the original recovery barrier only if the captured Runtime is still current, uses one platform UUID-named `reader-platform-atomic-*` scratch in the application's filesDir, and never reads production intents/user books/Core/Preferences. It reuses the actual IO helper rather than a second file writer. Only phase/status/character count/elapsed/code are logged, no URLs/body/paths/user identifiers. A diagnostic logger failure does not alter IO or startup. The probe may continue its accepted synthetic IO across UI retirement, without publishing any page state.

Successful exact write/read/empty-replacement ACK permits deleting only that scratch. A failed/unknown write retains the unique scratch and reports unverified; it never calls failWrite after finish or deletes the uncertain published result. This deliberate diagnostic residue is not a business intent and cannot authorize Core dispatch. A subsequent diagnostic invocation uses another unique name. No automatic loop/retry/timer, generic command endpoint or user-data reset is introduced.

Local `test-reader-atomic-snapshot-probe.mjs` exercises the actual helper and full probe, exact primitive opt-in, release/warm refusal, real original DTO shape, logger isolation and post-effect parent-sync failure. These are controlled platform IO fixtures. Complete ArkTS, exact signed HAP, current source/package hashes, target lease/boot/SceneBoard preflight and actual OS results remain necessary. Shared VM use must wait for the other active installation window; visual/user acceptance remain deferred.
