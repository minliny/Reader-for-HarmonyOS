# 控制栏展开/收起卡顿：本地录像与生产代码核查

2026-09-10，用户现场反馈：未看到翻页闪烁，但控制栏展开/收起途中卡顿和停留。按用户指令释放真机，后续设备验证仅使用 VM。本报告不把源码风险写成已完成的运行时归因。

## 当前生产路径

`LocalReadingExperience → ReaderControlPanel → ReaderControlRuntime`。

`ReaderControlMotionStage` 当前由验证页使用，生产 Panel 没有挂载它。因此该 Stage 的缓存、首帧计时或调度行为不能直接解释生产现场，也不能只优化验证页后宣布修复。

## 源码已确认的机制

1. **同一帧反复计算完整几何。** `ReaderControlPanel.frame()` 每次重新构造完整运动布局，同一 build 中有数十处调用；`controlQuickHeight()` 还会重新创建几何对象。生产路径没有按当前进度和布局复用同一计算结果。
2. **动画同时触发实际布局。** Panel 逐帧更新 `visualSession`，改变内容实际宽高；文字、列表、动态路径裁剪和模糊一起更新。这不是单纯合成器位移。
3. **目录每帧还调整滚动位置。** 目录 progress watcher 在行高/列表宽高变化时调用 `currentOffset()` 和 `scrollTo()`，增加布局与滚动同步的压力。尚无 trace 证明其耗时超预算；也没有证据认定存在无限 AreaChange 循环。
4. **清晰度存在固定平台。** `ReaderControlMotionPresentation.ts` 在展开进度 0.2–0.8 内保持 opacity=0.35、blur=2。这是已有呈现规则，会形成模糊程度维持一段的观感，不等于动画时钟停止。
5. **自动曲线尾部很慢。** 生产 open/morph/dismiss 共用 cubicBezier(0.2,0,0,1)。数学采样中，前半时间已走完约87.78%的路程，最后四分之一时间只剩约2.45%；320ms展开的最后80ms位移很小。这可能解释近端停留，不能解释任意位置的真实冻结。
6. **动态裁剪与过滤有额外开销。** 外观模块重复计算端点几何、生成 PathShape；多个模块在中段保持模糊绘制。需要 VM 的 UI/GPU trace 判断主导成本。

未发现普通展开/收起中段有主动 sleep、固定等待计时器或丢弃长帧 elapsed 的逻辑。Runtime 按真实时间差推进；UI 线程若延迟，会停到下一次回调再追赶。

## 下一轮 VM 应验证什么

1. 先确认原有 VM 身份、启动完成、SceneBoard 稳定及独占锁；使用 manifest 绑定且保数据的当前包。不得自动新建、重置或更换 VM。
2. 录制完整「快捷→完整→快捷」，分别测试点击、慢拖、收尾中重新抓住、深滚后收起，覆盖目录、界面、朗读等不同内容体量。
3. 将同一次动作的单调时钟、进度p/v、epoch/ticket、布局revision与帧耗时关联。区分壳体仍在移动而清晰度固定、曲线近端慢尾、UI/RS真实长帧三种情况。
4. 确认瓶颈后，优先在生产 Panel 缓存唯一几何帧和端点几何，减少动画中实际布局与同步滚动，缓存裁剪路径。不能直接削短时长或改变轨迹掩盖掉帧，也不能把现有变形过程替换为淡入淡出。

本轮未修改业务源码，未在 VM 上声称通过。源码中的开销机制与时间轨迹已核查；控制栏卡顿的设备级根因仍需上述对应场景取证。
