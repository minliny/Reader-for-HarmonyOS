# Image origin code audit

The new independent actual-SDK probe runs against the frozen temporary R7 production source and existing SDK/property helpers through absolute paths. It is stored in this evidence directory and does not modify canonical tools, fixtures, source, SDK or the 437 input set. The command exits 0; its source/helper/compiler hashes are in SOURCE_REQUEST_VALIDATION.json.

Both source-fit (a controlled manifest explicitly requesting width) and explicit width-fit select the actual production Projection's first ordinal/tile/sourceY=0. Actual production rowDisplayTop/Left return 0 and Image/row requested heights match. The unchanged emitted Image uses the SDK-declared ImageFit.Fill value. Root/stage/Canvas/Scroll/List/ListItem/Image actors request no padding, margin, translate, offset, position, transform, renderFit, aspectRatio or objectPosition. Actual controls toggles and metrics updates preserve admitted actors, URI, dimensions, row key, anchor and viewport requests and issue no restore/scroll under controlled full-window Area/Scroller inputs. Two narrow in-memory changes to the actual production Image (margin.top24 and Fill->Contain) fail the intended actual SDK emitted actor assertions. No watcher, expected geometry policy or image fitting algorithm is substituted.

The controlled 1600x2667 page / 655-row tile is a geometry fixture, not an assertion about the current source's measured encoded dimensions. Source-fit requesting contain is deliberately outside the zero-centering claim: the existing application explicitly centers contain mode by design.

Code trace: MangaReadingSurface.Image reads controller.tile.image.fileUri directly (1322), sets width and matching source-aspect height plus Fill (1323), and the List has space0 (1318). MangaSessionController.loadTileOwned forwards normalized tile position to MangaResourceGateway, which passes it to ReaderRuntimeOwner. Runtime loads exact persistent prepared bytes or prepares them through Core, then ReadingBodyImageHost.withDecodedPixelMap requests a bounded region. Region0 starts at the normalized source y0 (encoded coordinates account for EXIF); raw decoded dimensions and normalized region dimensions are checked. The display path for a region is cacheDir/reader-body-display-v1/reading-body-g{generation}-{width}x{height}-{preparedByteSHA}-region-0.png. performDisplayFileWrite packs the received PixelMap directly to PNG: no added Canvas, padding, pixel offset, tint or background fill. The optional source-script graphics path also validates complete source and target strip coverage with unchanged dimensions; it may reorder content per source rules, so source metadata is still needed.

Persistent bytes are Host files, not SQLite blobs: filesDir/reader-offline/images-v2/{SHA(JSON[sourceId,bookId])}/{chapterIndex}/{SHA(contentVersion)}/{resourceHash}.bin. identity-v1 hashes [manga-resource-v1,contentVersion,resourceRef]; bytes-v1 adds the fixed script-bgra-v2 profile via [manga-resource-v2,profile,contentVersion,resourceRef]. Core identity and requests live in filesDir/reader-core/reader-core.sqlite3: manga_page_index payload/request, manga_manifest_meta, manga_heads. No source URI is exposed by the current UI dump; ordinary production logging does not publish successful fileUri. Reading the current live display PNG first is the minimum sample required to associate the rendered content.

The actual A dump reports first ListItem/Image bounds/origBounds y0..524; screenshot top is pale blue (238,247,255), while the production underlay is warm paper F8F4EC. The same blue appears in the outer image borders and after the cover, supporting a source-content hypothesis. This is not sufficient evidence to conclude the original has that margin: no exact displayed PNG or original prepared bytes have yet been read. The source chain excludes an authored warm-paper safe-area band and explicit host padding as its cause; a native decode/paint issue and actual source content remain distinguishable only after byte/PNG association.

Boundary: installed SDK compiler/property classes execute; native rendering, codec pixel outputs and OS Area delivery are not simulated. Zero origin and Fill are native requests, not proof of the screen's first mapped source pixel. Exact original/prepared byte and displayed PNG comparison remains pending parent authorization. No source crop/trim behavior or hardcoded offset is proposed.
