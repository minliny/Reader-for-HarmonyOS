父清单为 `reader-source-inventory.json`；配套 Native SDK 父归档 SHA-256 为 `0100e26efb0589baf76ca449bcd5aaeba7000e61e856879a99d3ff4268e3355d`，设计源码父归档 SHA-256 为 `1415dbf6f7c334fbf967c8e7e1a6b229a5f8be76737e83ff74f72a6079539dd0`。三者保持冻结。

收到最终文件集合后依次执行：

1. 只读核对独立交付树与原工作树最终文件的 SHA、字节和权限，确认完全一致；清单逐项记录父档里的旧 SHA 和最终新 SHA。父任务未明确给出的变化必须先报告，不靠 dirty 列表猜测范围。
2. 仅收录明确新增、修改或删除的源码路径。修改项必须与父清单的旧记录精确匹配；新增必须在父清单中不存在；删除只在明确授权且旧记录匹配时生效。归档 payload 路径沿用 R4 的仓库前缀，避免还原时猜路径。
3. 生成独立 R5 delta 归档及清单，绑定父归档全 SHA、父清单 SHA、每项操作与旧／新记录、delta 自身 SHA。沿用私有材料排除检查，不打包证书、密钥、Profile、依赖目录、缓存或活动日志。
4. 完整读回 delta 每个文件，检查 SHA、字节、权限和精确成员集合。再从 R4 父档逐文件读取，按明确 delta 应用到新的验证临时目录，核对重建后完整有效源码清单，确保未列出的文件逐字节保留父版本。
5. 将重建结果与冻结的最终交付树比较，在规范源码输入范围内核对一致，保留有效清单及其指纹；直接重算 Core 构建输入，确认本轮若未改 Core 仍为 `9e97919470b42d81d87082c2c257984778da5e5e5e55798273b3242c99608c4b`。
6. 等父任务给出最终规范 R5 run，另保存其公开 manifest 与必要 SDK／源码绑定记录的 SHA，绑定本增量有效清单、HAP SHA、Host SO SHA、Core 输入指纹及 SDK package manifest。若 Native 未变，引用已验证的 R4 Native 父归档；若发生任何绑定变化，先报告并只按最终事实保存新包。

还原链为“R4 冻结源码父档 + R5 明确文件 delta”；Native 与 demo 分别引用已冻结父包。归档与重建只证明源字节和绑定关系，不能替代规范构建、验签、VM 绘制或用户视觉验收。原规范 run 和 VM 原件由父任务负责，保存时也不覆写已冻结 R3／R4 证据。
