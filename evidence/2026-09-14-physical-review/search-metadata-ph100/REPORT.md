## 已定位原因与修复

1. **源规则拼接了展示文案。** 单源真实搜索 HTTP 200，目标原始书籍 ID 为 `1793242`，`intro` 为真正简介，`ptags` 为独立标签，搜索结果没有任何最新章节字段。原源模板将两者拼入 `intro`，两行卡片先被标签占据。本次只升级这一内置源至 v7：搜索/详情直接读取 `intro`，标签保存在 `kind`，详情保留原有日期信息；没有改作者、卡片尺寸或同名书分组。
2. **Host 回调后丢失书源执行作用域。** 搜索 URL 的 `java.put('headers',…)` 写入源变量，回调重置工作线程上下文，后续解析未重新绑定源，`java.get('headers')` 读取全局空间而返回空值。真实 VM 日志与原始响应重放都出现尾部逗号但无请求头的详情地址。Core 现在在每个解析入口恢复正确书源与 Cookie 会话，覆盖详情、目录和正文分页等相同边界；没有重写签名或改成全局共享参数。
3. **空目录被错误归类为版本冲突。** Core 的 `catalogInstalled=false` 同时可能代表目录无可读条目或过期结果未发布。Host 原先一律按后者处理，导致同书候选不再继续。现先校验身份/版本，再区分空目录和真实过期发布；固定书架身份/显式选源不会被自动换掉。原 VM 日志不能单凭该旧文案证明竞争，因此没有宣称发生了并发覆盖。
4. **缓存空字段覆盖已有有效元数据。** 同源同 URL 的空字符串/空白缓存曾覆盖已知简介、封面、类型和最新章节。现在仅该精确身份保留既有非空值；不同 URL、源或过期版本不能借此继承元数据，导航参数也不随展示补全更换。

详情返回后的既有通知与搜索缓存投影链保留，用它补回最新章节；不伪造搜索接口没有返回的章节，也不为每条结果另开一轮全源网络扫描。
