## 2. 当前实际数据链路

1. 搜索结果先进入同书分组，保留每个 `(sourceId, bookId, ruleVersion)` 候选及搜索变量。
2. 可见区域最多 6 个同书组，最多同时 2 个后台任务做详情和目录准备；**不准备正文**。
3. 点击搜索结果，优先使用已准备目录；详情/目录失败时可改试同组候选，但未知候选最多 3 个。
4. 一旦某候选详情/目录通过，就安装该源会话并开始另一条正文验证。新书最多尝试该源前 3 个可导航章节，且仅空正文允许继续下一章；续读只检查保存的指定章节。
5. 正文失败更新详情页 verdict，**没有回接步骤 3 自动尝试下一书源**。
6. 手动换源已能复用点击时的候选和 Core 的相关候选缓存；空缓存或主动刷新才搜索更多源。

主要代码：[Coordinator](../../../entry/src/main/ets/app/BookAcquisitionCoordinator.ts:173)、[Index 选源](../../../entry/src/main/ets/pages/Index.ets:2657)、[正文验证](../../../entry/src/main/ets/pages/Index.ets:4738)。

## 4. 已排除或必须纠正的判断

- 当前不是“搜索结果从不复用，换源必定全量重搜”：点击候选及相关缓存已有复用，真正剩余问题是正文失败的候选回退断点、空缓存/主动刷新批次等待，以及具体失败场景为什么未命中既有候选缓存。Index 已有变更订阅与串行归并，不重新列作“完全未同步”。
- 不是所有 Core 解析错误都被显示为网络错误：结构化 `SOURCE_RULE_FAILED`/`SOURCE_RESPONSE_FORMAT` 在 `RemoteReadingContract.ts:340` 转 `invalidResponse`，本轮实际方法验证得到 `SOURCE_PARSE_FAILED`。问题集中在更早已吞掉的错误和没有结构化分类的失败。
- 不能把一个章节失败永久标成整本书所有章节失败；当前章节级失败与全书失败分开，是应保留的数据约束。
- 自动换源不能改变已入架书的 source/book 身份、进度或书签。新书试读与已保存阅读会话分开处理。
- 不能把 `198.18.*` 放进正常公网准入来绕过 VM 网络问题；该次受限网络环境与真机有效搜索结果是两份证据。

## 5. 修复顺序与完成条件

1. **先修错误结果准入和错误原因保留。** 对真实源规则回放建立三种明确结果：合法文本、合法空内容、响应/规则失败；错误日志和 API message 不能发布 readable。复用当前 JSON/HTML/JS 开源依赖及既有 Core 规则引擎，修改必要业务适配，不另造解析器。保留原始缓存、正文版本和位置迁移约束。
2. **合并新书候选获取与正文验证。** 已准备目录立即展示；首次可读候选继续后台选择，在相同可信书籍身份内自动试下一源。可见组仍有窗口与并发预算，不能给所有结果同时预取正文；前台不把“本轮只试 3 个”冒充“全组不可读”。阶段、尝试数、总时间预算、取消均进入同一过程；当前默认单请求 30 秒但没有整条候选链 deadline，不能叠加等待到用户不知进展。
3. **修调度与已有性能缺口。** 换源消除 8 源批屏障；Core 为前台获取与 JS 同步等待明确资源预算。当前已有的稳定 publication/共享 FIFO 修复继续保留，真实网络下再记录首个准确结果、首个可读源、UI响应与慢源占用。
4. **完成 PH76 隔离修复及真实回调验证。** 旧 resource/pageBegin/pageEnd/network/detach 不得污染新任务；合法同 URL 新回调仍工作；未挂载取消/超时及 controller 创建异常可恢复；实际新资源回调和 matched 事件都出现才算 cancel 场景通过。
5. **补逐源质量记录，保持已有动态候选同步。** 一次查询持久/诊断关联 query、源规则摘要、书籍身份摘要、detail/TOC/chapter阶段、HTTP/规则分类、耗时、重试顺序、缓存版本及成功章节。失败记录不能只剩通用“不可读”。保留 Index 已有变更订阅与串行归并；显式刷新才重搜已知源。补单条畸形记录隔离，保存失败计数与最小诊断，不让合法兄弟条目丢失。
6. **再做限定的真实链路核验。** 首先回放已获得原响应；代码侧无法判定时才按原设备规则获取同次鸣龙的最小失败样本。每个失败源单独归类：连接/认证/规则/格式/空目录/空正文/位置保护/客户端错误；成功源验证首章和后续章节，不用 TOC 成功代替正文可读。

闭环必须同时满足：同组可用源不会因前几个失败而漏掉；正文错误不会被标可读；失败原因可追溯；搜索、详情、换源共用候选/缓存；回退不损用户进度；可读结果到达时 UI 可交互；同一最终包的 VM/真机记录与人工验收独立保留。构建通过和测试数量不能替代以上条件。

## 6. 仍缺的证据，非用户决策

- 最新修复是否覆盖用户这次真机问题，需要同一最终包验证。最后真机部署记录与当前 VM 不同包；没有实时检查不能声称用户手机一定仍在旧包。
- 这些都不要求用户重新设计交互、回忆原书源名或决定新需求。先完成明确的代码修复，再对仍无法定位的最小真实样本取证。
