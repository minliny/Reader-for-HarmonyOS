# Reader settings persistence and window truth

Input: integrated Host `746b7b16`; independent `codex/p3-reader-settings-write-facts-20261003`. No Index, public Theme/Typography, Native/HAP or device changes.

The full P3 responsibility review found a remaining A31 sibling. `ReaderSettingsGateway.update` serializes by Runtime even though successors write the same Preferences file. Its catch writes the previous value after any put/flush rejection. A flush ACK can be lost after durability; that compensation can overwrite the actual user choice. LRE independently rolls session toggles, native window policy and page-turn/navigation style back after that same unknown error. ReaderSettings migration swallows flush uncertainty and warm successors do not share the accepted snapshot. Existing source/geometry tests do not inject that actual Preferences timing.

Required boundary: one file-local IO lane across Runtime/Ability owners, accepted/current snapshot independent of actual flush-confirmed snapshot/revision, one finite same-snapshot retry guarded against a newer choice, no cached-get durability inference and no compensating write. Before first put, check captured Runtime/lifecycle/book/operation admission after restore/store/serial/read waits. After put, retirement must not cancel flush or release the native IO lane. Native window refusal remains separate from preference save uncertainty; only a real window-policy refusal may restore the previous visible policy before accepting a settings write. Page-turn/navigation and rendering tuples remain unchanged by missing preference ACK.

Cold load is a loaded preference baseline, not a retroactive ACK from a previous process. Warm replacement preserves current accepted choice and unknown facts. Legacy migration uses the same existing normalization and one Preferences lane, retains a usable normalized snapshot on unconfirmed flush and retries only the same whole snapshot. Configuration reset keeps the existing two-argument `update(snapshot,true)` API and existing recovery ownership.

Code/method, formal ArkTS/HAP, OS Preferences durability, target/native window behavior and visual/user acceptance remain separate. This lane does not use a target device or claim process-kill durability for in-memory accepted facts.

## Implemented boundary and evidence

The actual SDK-emitted original Gateway reproduced `flush` copying the requested snapshot to durability and then rejecting its ACK; the old catch issued another `put(previous)`, leaving cache and durable values different. The candidate removes that compensation, uses one static Preferences-file tail and retains accepted vs actual flush-confirmed snapshots/revisions. The last dispatch admission checks actual Runtime and the captured UI predicate after restore, serial, store opening and baseline read. Once put begins, the actual IO lane remains held through flush even after a Runtime replacement. Warm reads return the accepted choice without declaring it saved. A finite `retryAccepted` reuses the original whole snapshot and a revision guard; it cannot overwrite a newer choice. Overflow rejects before put. Legacy normalization/schema and reset parameters remain unchanged; migration uses that same lane and write facts rather than swallowing its uncertain durability.

LRE session toggles, window-backed settings and page-turn/navigation style keep the current selected state after a Preferences error. They publish “阅读设置保存尚未确认，当前效果已保留，请稍后重试”. A window-policy failure that occurs before preference dispatch still restores the previous actual window policy and reports its own failure. A later preference failure cannot masquerade as that native refusal. Warm restored and ordinary settings loads both schedule one nonblocking finite retry only when actual write facts remain pending; no loop or cached-get durability confirmation is added. Captured lifecycle/source/book/generation rejects obsolete queued writes and notices. Diagnostics and toast failures cannot restore old policy. Rendering, measurement, persistent trees and geometry remain at their original owners/values.

`test-reader-settings-write-facts.mjs` emits the whole actual Gateway through the installed SDK and executes actual LRE methods. It covers put-before-effect rejection, flush-before-durable failure, durable-flush lost ACK, same-file warm Runtime ordering, restore/serial/store/read retirement, old retry rejection, safe revision exhaustion, legacy migration uncertainty, invalid/cold values, four real session/window/style/continuous mutations, independent native refusal, late lifecycle/book/operation and both startup-loading paths. Two mutated-production controls reproduce the previous Gateway compensation and LRE rollback. Existing settings, page-turn, window-chrome ordering, entry presentation, startup reading-settings and actual configuration-reset tests preserve their geometry/native lifecycle assertions; old tests that labelled current state as confirmed were updated to assert the separate write facts. The new test requires installed SDK (`integration` tier).

Rollback is the Gateway and three LRE save consumers/one retry consumer together. Reverting to compensation against an unknown flush may overwrite already durable user intent and is not an honest recovery action. This change uses the existing platform Preferences and Reader normalization; it creates no Core command, schema, native lease, generic settings bus, layout engine or new UI variant. Actual OS flush durability and window scheduling remain target gates.
