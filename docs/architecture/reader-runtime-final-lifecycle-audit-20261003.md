## 1. Image leases — implemented candidate

`ReaderReadingImageResources` owns only this reader's retained acquisitions, original URI/PixelMap identity, duplicate-acquisition balancing, pruning and close. It captures the actual allocator at construction. BodyImageHost remains the native/file refcount owner; no second cache, decoder, or refcount was introduced. LRE supplies its real retention predicate because current chapter, pending selection origin/candidate, retained chapter window and prepared/visible fragments belong to its presentation transaction.

All cleanup paths delegate to that captured owner, including unadmitted late acquisitions. Retiring the static Runtime cannot redirect cleanup to a new Runtime or interrupt paragraph/window/observer/coordinator/measurement cleanup. Thrown release calls are counted and diagnostics isolated; they have no atomic native release receipt, so they are not blindly replayed or claimed confirmed. Existing Ability-level display-file cleanup remains the fallback. The pool supports reuse after close without remounting the tree.

Evidence: `test-reader-image-resource-lifecycle.mjs` executes the actual owner and actual LRE cleanup/retention methods after static Runtime retirement, plus duplicate acquisitions, pending late images, close idempotence and release/diagnostic exceptions. `test-reader-known-image-geometry.mjs` continues the actual geometry→publication→lease path. Existing pagination and recoverable-entry regressions are unchanged in meaning. This is code/method evidence, not native deletion, ArkUI compositor, HAP, device, visual, or user acceptance.

Rollback: revert the image-owner commit as one unit (new owner, LRE callers, fixtures/tests/registration/document). Reverting only the leaf wrapper would reintroduce static Runtime teardown lookups.

## 2. TTS preferences — implemented lifecycle candidate

Seven preference mutations (mixing/background/keep-awake/failure policy/follow/pause-on-interruption/voice) currently guard only a mutation counter. A retired instance or changed book/coordinator can publish/rollback into a later lifecycle, and a queued gateway update may dispatch after retirement. The candidate captures lifecycle, source/book, coordinator and operation counter; it rejects before actual dispatch after restore/serialization/store-read waits. Once a real durable write was dispatched, retirement must not cancel its completion. Do not transplant playback state or policy to a global owner; retain the existing preferences gateway and coordinator owners.

Evidence: `test-reader-tts-preference-lifecycle.mjs` executes the actual complete preferences gateway and seven actual LRE mutation methods. Deferred restore, previous serial write, store opening, baseline reads, native policy/voice ACK, dispatched-write completion and retired lifecycle/book/coordinator/operation negative cases are covered; a generation-only production-source mutation is detected. Existing two-argument reset behavior is preserved. `test-reader-tts-preferences.mjs` remains passing. This is method/contract evidence; the existing native Preferences flush/rollback path has no atomic durable receipt, and this lifecycle change does not claim to solve that separate ambiguous-flush contract.

Rollback: revert the TTS preference admission commit as one unit. The optional third gateway argument is backward compatible; removing only the LRE caller would lose UI admission, while removing only the gateway check would allow queued retired writes.

## 3. Reading statistics — implemented bounded contract candidate

`ReadRecordAccumulateParams` has deviceId/bookName/author/elapsedMillis/readAt but no operation identity. `read_record_accumulate` delegates directly to storage addition. Both storage implementations atomically merge time; atomicity is not idempotency. Gateway only validates aggregate ACK, and LRE restores delta on any catch then repeats it. A missing ACK after commit can add the same delta twice. `flushReadingRecordForExit` retries once and then returns even when the second catch requeues data: the current failure path can therefore deliver route exit with unconfirmed duration.

The final contract uses one fixed Core cache row `reader.read-record.delta-head.v1`, not an unbounded receipt per 30-second interval. It holds only a safe monotonic sequence and the latest exact delta/record receipt. Operation identity is the existing Host installation device UUID plus sequence (`deviceId/sequence`). Latest same identity and exact payload replay returns that receipt; same-sequence conflicting payload/identity, old sequences, gaps, and sequence overflow are rejected without addition. New statistics and head commit in one SQLite IMMEDIATE transaction, with equivalent in-memory locking. Legacy calls without the optional identity/sequence retain their original semantics and do not reset the watermark. Statistics reset keeps the head; cache clear and external snapshot authority protection are integrated by the P4 single writer. Internal exact before-image rollback stays exact. No SQLite/ABI/protocol version upgrade was introduced.

Host `ReadingRecordGateway` serializes one Preferences journal across Runtime/Ability owners. Its pending or confirmed snapshot is bounded and contains a fixed accepted delta, exact identity/sequence and (once confirmed) the real Core receipt. Journal put/flush ACK precedes native dispatch. Exact native ACK or read-only latest receipt precedes marking confirmed; the confirmed snapshot's actual flush ACK precedes the next delta. Cached get alone never confirms a durable flush. Retired Runtime cannot overwrite/clear the new actor's journal. Cold readers reconcile the old pending producer before admitting their own delta. A single latest receipt cannot prove an old pending sequence after another actor advanced the watermark: that case remains explicitly blocked. It is not inferred from aggregate statistics and is not replayed with a fresh sequence. This is the deliberate bounded-history tradeoff, with retry/read-only or continue-reading recovery and no hidden discard action.

`ReaderReadingRecordHost` owns the real 30-second clock, unaccepted elapsed scalar, one accepted delta and coalesced durable work. Unknown failures retain that exact delta instead of restoring it into fresh elapsed time. A 15-second exit presentation deadline leaves the actual IO lane held; retry cannot dispatch a competing journal while old IO is pending. Failed/unknown duration exits reach the existing native confirmation family with an honest duration notice, retry or continue reading. They do not silently deliver route exit after two failed catches. Forced teardown starts no new write; accepted/dispatched journal work is not cancelled merely because UI retired. Unaccepted elapsed time remains bounded in memory as before; a missing local flush ACK is not claimed persisted across a process kill.

Code/method evidence: `test-reader-reading-record-receipt.mjs` executes actual Gateway/Host/LRE paths with pending/confirmed Preferences ACK loss, native ACK loss, cold/current Runtime, identity collision, head-superseded blocked unknown, safe sequence exhaustion, cross-Runtime serial lane, coalescing, timeout and exit recovery. Actual SQLite/in-memory tests `read_record_delta_receipts` cover exact replay, altered payload, old/gap sequence, statistics clear, cache clear, 1000 intervals/one head, atomic second-row failure rollback, cold reopen, two-connection competition and safe overflow. Core public DTO/schema/router/snapshot hooks were applied by P4; P3's private modules remained isolated. Runtime/contract integration test and storage Clippy are recorded separately.

Rollback: Host duration owner/Gateway/LRE/tests must move together, with a Core that provides the new optional identity and read-only receipt command. Older binaries still run schema 34, but older cache clear/full snapshot replacement code does not understand the new authority key and can erase it; do not call those old cleanup paths against this live ledger. Never reset the head or erase a pending journal to make unknown look successful.

## 4. Remaining TTS Preferences ambiguous-flush contract — next candidate

The existing `ReaderTtsPreferencesGateway.update` compensates `put(previous)` after any put/flush error; seven LRE catches also roll temporary policies back. A lost flush ACK may already be durable, so that compensation is unsafe and the saved/accepted facts are compressed. This is a real source/presentation-owner gap, not a permanent platform excuse. The follow-up must serialize the same Preferences file across Runtime owners, retain one exact desired whole snapshot, distinguish accepted from saved revisions, rely only on actual flush ACK and avoid cached-get confirmation. Exact whole-snapshot setters can retry idempotently; reading-duration deltas cannot use that shortcut. Root owns the matching appearance-store audit; LRE appearance wording will say saving is not yet confirmed.
